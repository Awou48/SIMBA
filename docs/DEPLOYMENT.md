# Deploying SIMBA on a free tier

Three pieces have to be hosted: the FastAPI API, a PostgreSQL database, and the `frontend/` static bundle
(which serves both the parent website and the Health Manager portal). `render.yaml` in the repository root
declares the first and the third as a Render Blueprint; the database comes from Neon.

Checked October 2026. Free-tier terms change — re-read both providers' pricing pages before you rely on them.

| Piece | Where | Free-tier terms that matter |
|---|---|---|
| API (`backend/`) | Render web service, `plan: free` | 512 MB RAM, 0.1 CPU, 750 instance-hours/month per workspace, **sleeps after 15 minutes idle** and takes roughly a minute to wake |
| Database | Neon | 1 GB per project (raised from 0.5 GB on 2026-10-01), no expiry, scales to zero |
| Web bundle (`frontend/`) | Render static site | free, always on |

Render also offers its own free PostgreSQL, but that instance **expires 30 days after creation**, so it is not
suitable for an archived project. Neon's free plan has no time limit.

The seeded database is small: 1,651 foods, 366 WHO percentile rows, 20 KPSP questions, 4 AKG brackets,
4 articles. Measured memory for the API after serving requests, including PDF generation, was about 133 MB.

## 1. Database

1. Create a Neon project and a database.
2. Copy the connection string. It must keep `?sslmode=require`, and it has to start with `postgresql://`
   (SQLAlchemy does not accept Neon's `postgres://` form), for example:
   `postgresql://user:password@ep-xxx.region.aws.neon.tech/simba?sslmode=require`

## 2. API and web bundle

1. Push this branch to GitHub.
2. In Render, create a new Blueprint from the repository. It reads `render.yaml` and proposes two services,
   `simba-api` and `simba-web`.
3. Render prompts for every variable marked `sync: false`. Fill them in:

| Service | Variable | Value |
|---|---|---|
| `simba-api` | `DATABASE_URL` | the Neon connection string from step 1 |
| `simba-api` | `CORS_ORIGINS` | JSON list containing the static site's URL, e.g. `["https://simba-web.onrender.com"]` |
| `simba-api` | `FIRST_ADMIN_EMAIL` | the first Health Manager login |
| `simba-api` | `FIRST_ADMIN_PASSWORD` | a password you choose; change it after the first sign-in |
| `simba-api` | `FIRST_ADMIN_NAME` | display name |
| `simba-web` | `VITE_API_URL` | the API's URL, no trailing slash, e.g. `https://simba-api.onrender.com` |

   `SECRET_KEY` is generated by Render (`generateValue: true`). `ENVIRONMENT=production` and
   `AUTO_SYNC_SCHEMA=false` are already set in `render.yaml`.

4. The two URLs are only known after the first deploy, so `CORS_ORIGINS` and `VITE_API_URL` will be wrong on
   that first build. Set them once the names exist and redeploy both services.

### What the API does on each start

```
alembic upgrade head && python seed_db.py && uvicorn main:app --host 0.0.0.0 --port $PORT
```

`alembic upgrade head` creates or updates the schema — `AUTO_SYNC_SCHEMA=false` means `create_all` no longer
runs at import. `seed_db.py` is idempotent: it loads the WHO, AKG, food, KPSP and article reference data and
creates the superadmin the first time, and skips every table that already has rows afterwards. Both run again
on every cold start, which costs a few seconds and keeps the schema honest.

## 3. Verify the deployment

```bash
API=https://simba-api.onrender.com
curl $API/health                                     # {"status":"ok"} (first call may take a minute)
curl -X POST $API/api/v1/admin/auth/login \
     -d "username=$FIRST_ADMIN_EMAIL&password=$FIRST_ADMIN_PASSWORD"
curl -H "Authorization: Bearer $TOKEN" "$API/api/v1/admin/foods?limit=1"
curl -o /dev/null -w '%{http_code}\n' $API/api/v1/admin/foods      # 401 without a token
```

Then open the static site: `/masuk` should register and sign in a parent, and `/hm/login` the superadmin.
`docs/TESTING.md` walks the whole feature set and applies unchanged to a deployed instance.

Config mistakes to check first if something fails:

- browser console shows a CORS error: the site's origin is missing from `CORS_ORIGINS`
- the site tries to reach `127.0.0.1:8000`: `VITE_API_URL` was not set at **build** time (Vite inlines it);
  since the closure pass a production build without it throws instead, so this surfaces as a blank page with a
  console error naming the variable
- API logs `ValidationError` for `SECRET_KEY`: `ENVIRONMENT=production` with the placeholder key

## 4. Mobile app

The Expo app is a client of the same API; it needs no hosting. Point it at the deployed API with
`EXPO_PUBLIC_API_URL=https://simba-api.onrender.com` in `mobile/.env` and restart `expo start` — the value is
baked into the bundle at start time. Running it in Expo Go needs nothing else.

Producing installable Android/iOS builds requires an Expo account and `eas build`, and store distribution
requires developer accounts. That was out of scope for this closure pass and has not been done.

## Limitations of this setup

- The API sleeps after 15 minutes without traffic. The first request afterwards takes about a minute, which the
  clients show as a slow load; the mobile app gives up after 15 seconds and reports a connection error.
- 750 instance-hours per month covers one always-reachable free service, not several.
- Neon's free compute also scales to zero, so a cold request pays both wake-ups.
- No HTTPS certificate, domain, backup or monitoring work is included beyond what the two providers give by
  default.
- This has not been deployed from this repository. The Render blueprint and the start sequence were rehearsed
  locally against a throwaway PostgreSQL database with `ENVIRONMENT=production` and `AUTO_SYNC_SCHEMA=false`,
  but creating the Render and Neon accounts needs credentials and must be done by the repository owner.
